# PoE2 单物品价差助手规格（Draft v0.2）

> 本文定义当前单页产品方向；旧多步闭环规格与实现已移除。

## 1. 产品定义

产品只围绕一个用户选定的物品，读取它与三种核心通货之间的买入、卖出价格，并判断是否存在可执行价差。

核心通货：

- 崇高石
- 神圣石
- 混沌石

产品回答：

1. 用哪一种核心通货买入该物品最便宜；
2. 把该物品卖成另一种核心通货最划算；
3. 按维护中的核心汇率归一化后，组合价值是否增长；
4. 若要换回起始通货，按完整整数订单、当前库存和三笔金币费用计算后是否仍有可锁定利润；
5. 如果值得做，准确告诉用户买多少、卖多少、预计赚多少以及消耗多少金币。

产品不再向普通用户展示任意 3–4 步通货闭环。

用户不需要填写本金。系统根据实时订单的整数比例和库存，反向计算最小入场成本、每轮收益以及当前最多可执行轮数。

## 2. 两种交易结论

### 2.1 同币种回转（辅助推荐）

```text
崇高石 → 物品 → 崇高石
神圣石 → 物品 → 神圣石
混沌石 → 物品 → 混沌石
```

只需要读取两个独立实时报价：

- 买入：核心通货 → 物品；
- 卖出：物品 → 同一种核心通货。

两笔报价通过整数手数、库存、新鲜度和金币检查后，可以给出“可执行”结论。它解释简单，但同一市场的正反价格通常更一致，因此作为辅助机会保留。

### 2.2 跨币种价差（主推荐）

```text
崇高石 → 物品 → 神圣石
神圣石 → 物品 → 混沌石
……
```

买入成本和卖出收入币种不同，必须通过一条有方向的核心汇率归一化：

```text
崇高石 → 物品 → 神圣石 → 崇高石
```

界面仍以单个物品为中心，但计算上包含第三条核心汇率。只有核心汇率仍在有效期内，才能给出价值判断；否则只能显示“可能有价差，需刷新核心汇率”。

跨币种存在两种完成方式：

- **持有卖出通货**：用户只执行 `A → X → B` 两笔交易。系统用 `B → A` 当前汇率计算组合价值增长，但它属于“估值收益”，不是已经换回 A 的锁定利润。
- **换回起始通货**：用户继续执行 `B → A`。三笔订单全部使用当前独立报价、库存和准确金币费后，才显示“可锁定利润”。

MVP 以跨币种价差为主路径，同时保留同币种回转结果。

## 3. 最小数据集

### 3.1 一个物品的报价

对用户选中的物品 `X`，最多存在六个方向：

```text
崇高石 → X    X → 崇高石
神圣石 → X    X → 神圣石
混沌石 → X    X → 混沌石
```

不强制一次读取全部六个方向。默认顺序为：

1. 根据历史线索选择最可能盈利的一组跨币种买卖方向；
2. 先读取这两个方向；
3. 若失败，再提示下一组；
4. 用户也可指定只检查某一种核心通货。

### 3.2 核心汇率

跨币种比较只需要维护实际候选用到的有向汇率，不需要每次预读完整六方向矩阵。

例如候选为 `崇高石 → X → 神圣石`，只需额外维护 `神圣石 → 崇高石`。正反方向不得通过取倒数推导。

用户选定起始通货 A 后，通常只需维护另外两种核心通货各自换回 A 的方向。例如以崇高石为起始，只维护 `神圣石 → 崇高石` 和 `混沌石 → 崇高石`；不会要求维护无关方向。

核心汇率采用以下生命周期：

- 在用户空闲或主动进入扫描时提示刷新；
- 在有效期内跨物品复用；
- 过期后只撤销依赖该方向的跨币种结论；
- 同币种回转不依赖核心汇率。

## 4. 用户流程

```text
选择物品或接受历史推荐
  → 系统给出最值得检查的一组方向
  → 玩家在游戏中设置买入方向
  → 应用连续被动读取报价与库存
  → 玩家设置卖出方向
  → 应用连续被动读取报价与库存
  → 系统计算最小整数订单、每轮收益和库存上限
  → 玩家直接在游戏中调整想执行的轮数
  → 应用自动读取游戏里的准确数量与买卖金币费并实时更新
  → 给出持有 B / 换回 A / 放弃
```

主流程不再包含：更新行情按钮、六个基础汇率前置清单、路线表、多路线共享清单或任意闭环选择。

## 5. 首页

```text
┌──────────────────────────────────────────┐
│ 单物品价差助手           数据正常   ⚙ ─ × │
│ 物品 [搜索或选择物品________________]    │
│ 起始通货 [崇高石⌄]                      │
│                                          │
│ 历史建议                                 │
│ 1. ××符文   可能价差 8.2% · 最低约 30 崇高 │
│ 2. ××催化剂 可能价差 5.7% · 最低约 12 崇高 │
│ 3. ××精华   可能价差 4.9% · 最低约 80 崇高 │
│                                          │
│                [检查所选物品]            │
└──────────────────────────────────────────┘
```

要求：

- 用户可以按名称搜索物品；
- 不提供本金输入框；最小入场成本和库存上限由报价计算后展示；
- 历史数据只推荐“值得实时检查”的物品，不展示为当前利润；
- 推荐必须显示数据时间、成交量等级和预计需要读取的方向；
- 最低入场成本是历史估计，只用于帮助选择检查对象；实时读取后必须重新计算；
- 默认最多展示 5 个推荐；
- 用户选择物品后，系统自动安排最可能有效的两个方向。

## 6. 自动读取

应用只观察游戏画面，不操作游戏。

```text
检测交易区域变化
  → 识别当前支付与获得物品
  → 确认与目标方向一致
  → 检测报价浮层稳定
  → 连续读取 3–5 帧
  → 对比率、库存和金币做一致性投票
  → 自动记录报价并计算
```

高置信度、多帧一致时自动接受；只有以下情况要求人工处理：

- 当前游戏方向与要求不一致；
- 物品名称与图标识别冲突；
- 比率、库存或金币在连续帧中不一致；
- OCR 置信度低；
- 浮层被悬浮窗或其他窗口遮挡。

## 7. 金币费用

### 7.1 为什么必须读取两次

一次完整操作至少包含：

- 买入订单金币费；
- 卖出订单金币费；
- 跨币种回转时的核心通货转换金币费。

金币费用与游戏中实际输入的订单数量相关。不能假设 `N` 份订单的金币费等于单份金币费乘以 `N`。

### 7.2 两阶段读取

第一阶段读取市场比率与库存，用于求出可盈利的准确整数数量。

第二阶段由玩家直接在游戏交易栏调整计划数量。应用观察数量变化，并重新读取游戏显示的实际金币费用：

```text
买入：支付 300 崇高石，获得 20 个物品，金币 42,000
卖出：支付 20 个物品，获得 324 崇高石，金币 37,000
```

对于两笔持有方案，买入和卖出的准确金币费都必须读到；对于换回起始通货方案，核心兑换的准确金币费也必须读到。若缺少任意依赖费用，结论最高只能是黄色“币值有利润，金币待确认”，不能显示绿色“可执行”。

### 7.3 金币不强行折算为通货

金币不能在 Currency Exchange 中自由兑换成崇高石，因此默认不把金币直接扣成某种通货价值。结果同时展示：

```text
通货净利润：+24 崇高石
金币总成本：79,000
金币效率：每 100 万金币约 +303.8 崇高石
```

用户可以设置两个独立门槛：

- 最低通货净利润或净收益率；
- 最低金币效率。

未来可以允许用户自行设置“金币影子价格”，但默认关闭，避免制造虚假的统一利润数字。

## 8. 订单与利润计算

### 8.1 报价模型

每个方向的报价必须包含：

```text
source_item_id
target_item_id
unit_ratio
order_pay
order_receive
available_receive
gold_for_exact_order
exact_order_quantity
observed_at
ocr_confidence
```

### 8.2 同币种利润

设买入订单为 `A 个核心通货 → B 个物品`，卖出订单为 `C 个物品 → D 个核心通货`。

系统求出最小整数倍，使买入获得的物品数量能够完整参与卖出，并受双方库存限制。随后输出：

- 最小一轮需要支付多少起始通货；
- 最小一轮能够获得多少卖出通货；
- 每轮利润和收益率；
- 当前库存最多支持多少完整轮；
- 玩家在游戏中选择的实际轮数对应的总利润和金币费。

计算方式：

```text
currency_profit = 卖出获得核心通货 - 买入支付核心通货
currency_roi = currency_profit / 买入支付核心通货
gold_total = 买入准确订单金币费 + 卖出准确订单金币费
gold_efficiency = currency_profit / gold_total
```

未能卖出的零头不计入主利润，只在详情中显示为剩余持仓。

### 8.3 跨币种利润

跨币种必须使用独立读取的有向核心兑换报价：

```text
estimated_value_profit = 按 B→A 当前单位率估算的卖出收入 - 买入成本
locked_profit = 真正执行完整 B→A 整数订单后的 A 收入 - 买入成本
```

- 只执行 `A → X → B` 时，展示 B 的实际增加量和以 A 计价的“估值收益”；
- 真正执行 `B → A` 后，展示“可锁定利润”；
- 仅使用历史核心汇率时只显示“历史估值”，不得给出绿色结论；
- 未能换回的 B 零头单独列为剩余持仓，不并入锁定利润。

## 9. 结果卡

```text
┌──────────────────────────────────────────┐
│ 跨币种机会 · 报价最老 12 秒              │
│                                          │
│ 300 崇高石 → 20 ××物品 → 3 神圣石        │
│ 按当前汇率估值 324 崇高石 · +8.0%         │
│ 两笔金币 79,000                            │
│ 库存最多支持 2 轮                         │
│                                          │
│ [买入并持有神圣石] [核验换回利润] [放弃] │
└──────────────────────────────────────────┘
```

结果只有三种：

- **可持有**：两笔物品交易通过，结果是增加另一种核心通货，并提供当前估值；
- **可锁定**：第三笔核心兑换也通过，能够计算换回起始通货后的利润；
- **观察**：币值存在利润，但金币缺失、利润低于缓冲或使用了历史核心汇率；
- **放弃**：亏损、库存不足、整数订单不成立或报价过期。

## 10. 历史推荐

历史数据不直接决定交易，只决定“先检查哪个物品”。

推荐分数考虑：

```text
可能价差
× 成交量可信度
× 数据新鲜度
× 整数订单可执行度
÷ 价格波动风险
```

优先推荐：

- 同一物品在不同核心通货市场中存在明显定价差；
- 买卖两侧都有足够历史成交量；
- 最小入场成本不过度极端，且当前库存能够形成至少一个完整整数订单；
- 近期价格没有明显断层或极端异常成交。

推荐文案统一使用“历史线索”或“值得检查”，不得使用“可赚”“可执行”。

## 11. 报价新鲜度

- 两个物品报价默认最大年龄：45 秒；
- 两个物品报价默认最大观测间隔：25 秒；
- 准确数量金币费必须在最终执行前读取；
- 任一依赖报价过期，绿色状态立即撤销；
- 同币种回转不因无关核心汇率过期而失效；
- 跨币种回转只刷新实际依赖的核心方向。

这些阈值属于策略配置，必须集中管理并通过真机测试重新标定。

## 12. MVP 范围

### 第一阶段

- 用户搜索并选择单个物品；
- 用户选择一种起始通货；
- 不填写本金；
- 根据历史线索优先检查一组跨币种买卖方向；
- 自动读取 `起始通货 → 物品` 与 `物品 → 另一核心通货`；
- 按需维护两条“其他核心通货 → 起始通货”汇率；
- 计算整数手数、库存、持有方案的估值收益和换回方案的锁定利润；
- 按最终准确数量读取买卖两次金币费；
- 用户要求锁定利润时，再读取核心兑换的准确金币费；
- 给出可持有、可锁定、观察或放弃结果。

### 第二阶段

- 历史数据推荐物品与方向；
- 自动依次检查三种同币种回转；
- 同时比较多个跨币种方向并优化扫描顺序；
- 持仓记录与退出建议。

### 不做

- 任意多物品、多节点闭环；
- 自动点击、切换交易对或下单；
- 游戏内存读取和客户端注入；
- 用历史价格直接宣称实时利润；
- 金币费用按单份订单线性放大。

## 13. 验收标准

1. 用户选择物品和核心通货后，只需在游戏中切换两个方向；
2. 高置信度报价无需点击“读取”或“确认”；
3. 系统只使用独立读取的买入、卖出和所依赖的有向核心汇率；
4. 主利润只计算能够完整买入并卖出的整数数量；
5. “可持有”必须包含买入和卖出的准确订单金币费；“可锁定”还必须包含核心兑换的准确订单金币费；
6. 报价过期后一个刷新周期内撤销绿色状态；
7. 库存不足时显示限制发生在买入侧还是卖出侧；
8. 历史推荐不能以实时利润形式展示；
9. 同币种机会不依赖核心汇率；跨币种机会只维护实际需要的换回方向，不要求六方向前置扫描；
10. 从选择物品到结论，应用内人工点击不超过 2 次。
11. 主流程没有本金输入框；系统显示最小入场成本、每轮收益和库存允许的最大轮数。

## 14. 开发前需要确认

1. MVP 默认给出“持有卖出通货”还是要求继续核验换回起始通货；
2. 起始通货由用户指定，买入/卖出方向由历史线索推荐；
3. 金币效率的默认最低门槛；
4. 当预计利润较高但准确金币读取失败时，是否允许用户手动填入；
5. 是否记录用户实际完成的交易，用于后续过滤经常无法成交的物品。
